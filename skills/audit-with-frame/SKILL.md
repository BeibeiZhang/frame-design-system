# Audit with Frame

Follow the user's explicit request, host permissions, and project instructions over this skill. Never claim a check ran unless you ran it and saw its result.

This skill provides instructions and packaged references, not callable Frame tools. Verify component and pattern claims against `references/`; if a reference cannot be read, identify that evidence gap and do not invent names, exports, capabilities, or results.

1. **Inventory the evidence.** Identify the target and what is available: source files, diff, screenshot, rendered page, description, or test results. State gaps before drawing conclusions; ask for the missing artifact only when it blocks the requested judgment.
2. **Load the review references.** Read `references/frame-rules.json` and `references/principles.md` for every Frame audit; they are separate sets of 11 implementation constraints and 13 design principles. Read `references/components.md` to assess released-component reuse, `references/ai-patterns.md` for AI interaction behavior, and `references/implementation-guide.md` for implementation and verification context. Read `references/real-products.md` only when real-product evidence matters. For source-code audits, also read `references/portable-checker.md` and `references/frame-check-coverage.json`.
3. **Verify the local checker before executing it.** When the host can run Node.js 20+ with the declared parser dependency already present, and the user supplied or authorized explicit local source files, first read the packaged `references/source-manifest.json` and get the expected digest from `sources.checker.sha256`. Compute the local `frame-check.mjs` file's SHA-256 with an available local implementation (for example, Node's built-in `crypto`, `sha256sum`, or `shasum -a 256`) and compare the full digest with that value **before invoking the file**. If the manifest or checker is unavailable, the digest cannot be computed, or the digests differ, do not invoke the checker; state that it was skipped and continue with a human-guided audit. Do not fetch a replacement checker, install dependencies, or send source to a service. Only after the digest matches, invoke that local file read-only with `--format json`.
4. **Use only the pinned checker profile.** Before interpreting any findings or clean result, require `schemaVersion: 1`, `checker: "frame-check"`, `checkerVersion: "1.0.0"`, and `coverageVersion: "frame-check-1"`. If a field is missing or differs, treat the result as incompatible, do not report its findings as Frame-check results, and continue with a human-guided audit. If any runtime, dependency, authorization, or other prerequisite is missing, skip the checker and continue as a human-guided audit.
5. **Review what the evidence can show.** Assess the applicable 11 implementation constraints, 13 principles, component/pattern truth, task states, AI trust and recovery, accessibility, responsive behavior, and light/dark presentation. Use direct code evidence or observed rendered behavior; a screenshot cannot establish code semantics, and code alone cannot establish rendered quality.
6. **Report actionable findings.** Order findings by user impact. For each, include severity, file/line or visible location when available, concrete evidence, why it matters, and a focused repair. Separate verified findings from unverified areas and strengths. State the exact checker command and exit code only if actually run; distinguish its supported subset from its human-only coverage.

The portable checker reports only partial-error subsets of FRAME-01–03 and one narrow FRAME-06 advisory. FRAME-04, FRAME-05, FRAME-07–11, and all 13 design principles require human review. Exit 0 means no finding in the supported subset, not certification. Never claim full compliance from a clean scan.
